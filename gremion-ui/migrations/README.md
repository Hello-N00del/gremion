# Database migrations (G-097)

Forward-only SQL migrations for the `gremion-ui` Postgres database. This README
is the source of truth for how migrations are applied, verified, and added.
When the runner, the manifest, or the file convention changes in code, this
file changes with it.

Related: the database-client lifecycle (`getDb()` lazy singleton) and the boot
gate are documented in [`../../docs/architecture.md`](../../docs/architecture.md)
("Database client lifecycle") and [`../../docs/auth.md`](../../docs/auth.md)
("Boot-503 short-circuit").

---

## How migrations run

Migrations live in this directory as `NNN_snake_case.sql` files and run in
**filename (lexical) order**. There are two entry points, both routed through
the same verified path in
[`../src/lib/server/db.ts`](../src/lib/server/db.ts):

| Trigger | Path |
|---------|------|
| **App cold start** | `boot()` (in `hooks.server.ts`) awaits `runFleetMigrations()` — the per-tenant fleet wrapper that runs this same `runMigrations()` once per ACTIVE tenant — before serving traffic. A CONTROL-plane failure populates `_bootError` (process-wide `503`); a single tenant's migration failure 503s only that tenant, with lazy retry. See ["Multi-tenant migration rules"](#multi-tenant-migration-rules-75) below. |
| **CI / manual** | `pnpm migrate` → `tsx scripts/run-migrations-verified.mjs` → `runMigrations()`. |

```bash
# from gremion-ui/
pnpm migrate
```

`pnpm migrate` resolves to `tsx scripts/run-migrations-verified.mjs`
([`../scripts/run-migrations-verified.mjs`](../scripts/run-migrations-verified.mjs)).
`tsx` is required (not plain `node`) because the runner dynamic-imports the
TypeScript `$lib/server/db.ts`; a SvelteKit env shim
(`scripts/sveltekit-env-shim.mjs`) resolves `$env/dynamic/private` so `db.ts`
can read `DATABASE_URL` outside the dev/preview server.

> **Why a verified runner exists (A-016).** The previous CI flow ran a raw
> `psql -f` loop that bypassed hash verification *and* never wrote
> `schema_migrations` bookkeeping — CI could apply a tampered or out-of-order
> migration and still pass while prod refused to boot. Routing CI through
> `runMigrations()` restores the same verification + bookkeeping path prod gets.

## Content-hash verification (`manifest.json`, G-012)

[`manifest.json`](manifest.json) maps each `*.sql` filename to the SHA-256 hex
digest of its bytes:

```json
{
  "001_governance_schema.sql": "b3d1f0a2…",
  "002_config_store.sql": "7c4e9d18…"
}
```

Before `db.ts` hands a file's text to `sql.unsafe()`, it calls
`verifyMigrationIntegrity(filename, text, manifest)`, which throws if:

- the filename has **no entry** in the manifest ("missing from manifest"), or
- the on-disk bytes hash **differently** than the manifest entry ("tampered").

Either case aborts the boot — a swapped or edited-after-the-fact migration can
never run silently. The manifest is regenerated by
[`../scripts/build-migration-manifest.mjs`](../scripts/build-migration-manifest.mjs)
(wired into `pnpm prebuild`, so every production build regenerates it against
the migrations actually copied into the image):

```bash
# from gremion-ui/  — regenerate after adding/editing any migration
node scripts/build-migration-manifest.mjs
```

The builder writes keys sorted lexically with 2-space indent + trailing
newline, so the output is deterministic regardless of host `readdir` order.

## The `schema_migrations` bookkeeping table

`runMigrations()` creates (idempotently) and reads:

```sql
CREATE TABLE IF NOT EXISTS schema_migrations (
  filename   TEXT        PRIMARY KEY,
  applied_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

For each `*.sql` file, in order, the runner skips it if a row with that
`filename` already exists; otherwise it verifies the hash and applies the file.

### Atomic per-file application (G-078)

`applyMigrationFile()` wraps **both** the migration body and its
`schema_migrations` INSERT in a single `sql.begin()` transaction:

```ts
await sql.begin(async (tx) => {
  await tx.unsafe(sql_text)
  await tx`INSERT INTO schema_migrations (filename) VALUES (${filename})`
})
```

So either the schema change **and** the bookkeeping row both land, or neither
does and the next boot retries cleanly. A crash between the two can no longer
leave a migration applied-but-unrecorded (which would then re-run a
non-idempotent DDL and explode on the first duplicate object).

### Seeds

Files ending in `_seed.sql` populate dev-only data keyed by dev-realm Keycloak
UUIDs. When `GREMION_DISABLE_SEEDS=true` (set in `docker-compose.prod.yml`) the
runner skips them, so production never applies a seed.

## House convention for migration files

1. **Filename:** `NNN_snake_case.sql`, zero-padded to 3 digits, `NNN` =
   (current highest) + 1. Files run in lexical order; never reuse or reorder a
   number that has shipped.
2. **Line endings: LF.** The hash is over the raw bytes — a CRLF would change
   the digest and fail verification on a checkout that normalises differently.
3. **No `BEGIN` / `COMMIT` inside the file.** The runner already wraps each
   file + its `schema_migrations` INSERT in one transaction (G-078). An explicit
   `COMMIT` would split that atomic pair. Four migrations that predate the rule
   still carry an explicit `BEGIN;`/`COMMIT;` — `041`, `042`, `043`, and a bare
   `BEGIN` opening a PL/pgSQL block in `008`. **Nothing warns about this**: the
   runner does not inspect the SQL text, so a new file that copies the pattern is
   caught by review or not at all. Do not copy it.
4. **Document the inverse.** Each migration's header comment states its
   rollback DDL (there is no automated `down` — rollback is manual / via
   restore).
5. **Forward-only.** Migrations are append-only; never edit a migration that
   has been applied anywhere — write a new one.

### Adding a migration — checklist

```bash
# from gremion-ui/
# 1. create migrations/0NN_my_change.sql  (next number, LF, no BEGIN/COMMIT)
# 2. regenerate the manifest
node scripts/build-migration-manifest.mjs
# 3. apply locally to verify
pnpm migrate
# 4. commit BOTH the .sql file AND the updated manifest.json
```

If you commit the `.sql` without regenerating `manifest.json`, boot fails with
"missing from manifest". If you edit a `.sql` after it was added to the
manifest without regenerating, boot fails with "tampered".

## Multi-tenant migration rules (§7.5)

Since Pillar 2 (P2.1a/P2.1b) one shared app image serves a fleet of tenants,
each with its own database, and the migrations in this directory are applied
**per tenant**. Everything above still holds unchanged *per tenant*; the rules
below are additional.

### Expand/contract — the tenet

A schema change ships across releases, never in one step:

1. **Expand (release N):** purely additive — a new table, a new nullable
   column or a column with a `DEFAULT`, a new index. Deployed code keeps
   working untouched.
2. **Dual-write/read window (release N):** the new code writes the new shape
   (backfilling / dual-writing where needed) while still being able to read
   the old one; nothing depends on the old shape being gone.
3. **Contract (release N+1 or later):** drop/rename/narrow **only after** no
   deployed code reads the old shape any more — as its own, later migration.

**Never ship a destructive change (`DROP`, `RENAME`, type narrowing,
`SET NOT NULL` without default + backfill) in the same release whose code
still reads the old shape.**

Why this is non-negotiable under multi-tenancy: the fleet runner applies the
chain one tenant at a time, and a failed tenant is retried lazily while the
rest of the fleet has already advanced — so the **one** deployed app version
**will** serve tenants on schema version N and N+1 simultaneously. Per-tenant
apply is also a safety upgrade (a bad migration is caught on one tenant before
fanning out to all of them) — but only expand/contract keeps that partial
state harmless.

### Fleet-runner semantics (per-tenant apply)

On boot, `runFleetMigrations()`
([`../src/lib/server/tenant/fleet.ts`](../src/lib/server/tenant/fleet.ts))
iterates the ACTIVE tenants from the control-plane registry — the `default`
tenant included, same path, no special case — and for each one resolves the
tenant and runs the standard verified `runMigrations()` inside
`runWithTenant(ctx, …)`, so every hash check, bookkeeping row, and transaction
rule above applies unchanged against **that tenant's** database (each tenant
has its own `schema_migrations`).

- **Outcome ledger:** every per-tenant run writes a row to the control-plane
  `tenant_migration_run` table
  ([`../migrations-control/002_tenant_migration_runs.sql`](../migrations-control/002_tenant_migration_runs.sql)):
  started/finished timestamps, ok/error, last applied filename.
- **Failure isolation (D-READY):** one tenant's failure never blocks the
  fleet. The failed tenant serves a tenant-scoped `503` with a single-flighted
  lazy re-migration retry (`../src/lib/server/tenant/readiness.ts`); every
  other tenant serves normally. Only a CONTROL-plane failure is a process-wide
  boot failure.

### Per-tenant module skip-logic (P0.2)

The module-deselection gate applies **per tenant, via that tenant's config**:
a disabled toggleable module's migration files (`disabledModuleMigrationFiles`,
[`../src/lib/server/module-migrations.ts`](../src/lib/server/module-migrations.ts))
are filtered out of that tenant's apply set and recorded **nowhere** ("absence,
not bookkeeping"). Consequences:

- Two tenants' `schema_migrations` tables legitimately differ, and numbering
  gaps inside one tenant's table are expected, not corruption.
- **OFF→ON re-enable (catch-up):** re-enabling a module on an already-initialized
  tenant is supported. `moduleReenableCatchup` (the pure planner in
  [`../src/lib/server/module-migrations.ts`](../src/lib/server/module-migrations.ts))
  reports the module's unapplied migration files; the standard apply loop then
  runs them against the advanced schema (they are absent from that tenant's
  `schema_migrations`, and — the module now being ON — no longer skipped). A
  module that was always ON with a newly-appended migration is a normal forward
  apply, not a catch-up. The planner never throws.
- **ON→OFF (retain):** turning a previously-initialized module OFF is a
  RETAIN policy — its schema and `schema_migrations` rows are left in place
  (no drop, no row removal); `disabledModuleMigrationFiles` only skips *future*
  forward application. So a later OFF→ON is a no-op (everything already applied).
- A migration owned by a toggleable module must stay self-contained in that
  module's schema: core (or other modules') migrations that a module-OFF
  tenant still applies may never depend on it.

### Numbering: the gaps are inherited, not corruption

The filenames in this directory are **deliberately non-contiguous**. They are
inherited from the pre-carve monorepo, and the missing numbers are migrations
that did not come across in the open-core extraction. The chain here is complete
and self-consistent on its own — `runMigrations()` applies files in filename
order and never requires contiguity — but it is a **strict subset** of the
reference product chain, and a fresh kernel install does not reproduce the
product schema. See [What is here, what is not](#what-is-here-what-is-not).

**Never renumber to close a gap.** The SHA-256 manifest and the
`schema_migrations` bookkeeping are keyed on these exact filenames; renaming a
shipped file makes every existing database report it as missing from the
manifest and re-apply it.

The next free data-plane number is **current highest + 1**, read off the
directory — never a number reused from a gap.

**The control plane is a separate chain.** The tenant registry and the fleet-run
ledger live in [`../migrations-control/`](../migrations-control/) with their own
independent `001…` numbering, their own runner (`runControlMigrations`) and
their own manifest (regenerated via
`node scripts/build-migration-manifest.mjs migrations-control`). Never number a
data-plane file against the control-plane chain, or the reverse.

the 36 absent files belong to feature modules that are not part of the kernel and
ship in their own repositories — calendar (`003`), finance (`013`–`017`,
`019`–`023`, `025`–`032`, `035`, `036`), content (`044`–`047`) and

accident:

| `049_org_unit_event_outbox.sql` | The org-unit event outbox. |

`055` and `056` are the schema half of the contestability / recall work that

signer configuration are finance-module concerns and are documented with the
finance module, not here.

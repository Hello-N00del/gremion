# Vendor mail runbook (TASK-015)

The vendor's own mail -- password resets of the operator realm, vendor news,
invoices, and the observability alerts -- is sent by the self-hosted Stalwart
Community Edition of the `${STACK}-mail` compose project (`infra/host/mail/`,
the TASK-040 five-project layout), on the vendor domain, and never through a
third-party mail API. This directory holds its tooling and guards; the licence
position is [docs/compliance/vendor-mail-licence.md](../../docs/compliance/vendor-mail-licence.md).

## 1. Identities (Q2) and custody (Q3)

| Principal | Secret (generator group) | Who sends as it |
|---|---|---|
| `system@<PLATFORM_DOMAIN>` | `VENDOR_SMTP_PASSWORD` (`vendor_smtp`, `mail.env` only) | the operator realm `master` (and the reserved `platform` realm) via `realm-smtp`; vendor news and invoices |
| `alerts@<PLATFORM_DOMAIN>` | `ALERT_SMTP_PASSWORD` (`alert_smtp`, `mail.env` + `ops.env`) | Alertmanager (`ALERT_SMTP_USER` = `ALERT_EMAIL_FROM` = this address; `check-identities`) |
| `roles@<PLATFORM_DOMAIN>` | `ROLES_IMAP_PASSWORD` | the operator's IMAP mailbox for the thirteen role aliases |
| `platform@<PLATFORM_DOMAIN>` | `PLATFORM_SMTP_PASSWORD` (`platform_smtp`, `mail.env` + app tier) | TRANSITIONAL: the app tier's realm sender until TASK-043; one allowance in `allowances.json`, retired by TASK-015-FU (G8) |
| `kc-<tenant token>@<PLATFORM_DOMAIN>` | generated at issue, held only by Stalwart and that realm's `smtpServer` | exactly one customer realm (TRD-049, L3-11) |

A customer principal's app password is generated by `principals issue`,
printed ONCE on stdout and never written to disk, an argv or git. A lost one
is rotated (`issue --rotate`), not recovered. `provision-roles.sh` refuses two
identities sharing one value.

Every authenticated message must carry its authenticated address as its only
`From` (`infra/host/mail/from-align.sieve`): `must-match-sender` binds only the
envelope, and a customer principal writing `From: system@...` was measured
being queued -- DMARC-aligned -- before that script existed. The script also
refuses a From with no mailbox and an address inside the display name
(`"system@<domain> Gremion" <kc-a@...>`); an RFC 2047 encoded display name is
not decoded by it (residual).

## 2. The launcher

The host has no Node. `infra/host/bin/gremion-vendor-mail` runs each check as
`docker run --rm` of `VENDOR_MAIL_NODE_IMAGE` (read from `mail.env` only, by
digest), with `ops/vendor-mail` mounted read-only, named
`${STACK}-vendor-mail-<sub>-<pid>` and labelled `gremion.stack=${STACK}`. It
runs from either layout: the release tree
(`/opt/gremion/current/infra/host/bin/gremion-vendor-mail`, which finds
`ops/vendor-mail` beside it), or the installed copy in `/opt/gremion/bin`
(`docs/ops/runbook/install.md`; first on `PATH`, and what a bare
`gremion-mail-bringup` calls), which takes `ops/vendor-mail` from the live
release `/opt/gremion/current`. With neither present it stops with exit 2 and
names both paths.

| Subcommand | What it does |
|---|---|
| `principals issue\|revoke\|list --tenant <token> [--rotate]` | the per-customer principal CLI; TASK-043's provisioning calls it through this launcher |
| `realm-smtp` | `master` -> `system@` via `mail.<domain>:587` STARTTLS; password on stdin; read back. `--realm/--tenant/--rotate/--revoke` are reserved for TASK-043 and refused |
| `collect --out DIR` | principal names/emails/roles and every realm's smtp user, secrets stripped |
| `check-identities` | alerts@ identity consistent across `mail.env` / `ops.env` |
| `check-received --file F --receiver NAME \| --authserv-id ID` | a delivered message's headers prove an own-server, SPF/DKIM/DMARC-passing delivery at ONE named receiver: only its authserv-id is trusted, and the accepting hop (and every hop above it) must be `by` one of its hosts (`hostSuffixes` in `deliverability/receivers.json`, or the mandatory `--receiver-domain` with `--authserv-id`). In bring-up, set `RECEIVER`, or `RECEIVER_AUTHSERV_ID` together with `RECEIVER_DOMAIN` (never both forms); otherwise 6a/6b are BLOCKED |
| `check-secret-separation --host` | value hashes: no vendor secret in `app-*.env`, `etc/secrets/tenants/**` or the running gremion-ui environment |
| `check-principals --host [--no-allowances]` | no realm shares a principal with another or with the vendor |
| `check-upstream-image`, `check-deliverability-record [--require]` | TRD-253 / TRD-252 |

**Network exception, stated:** every check runs with `--network none` except
`principals`, which needs the loopback management API (`STALWART_ADMIN_URL`,
`127.0.0.1:8086`) and therefore runs with `--network host` for the one call. It
is a transient one-shot and not a service of any compose project, so it sits
outside `scripts/check-pooled-stack.mjs`'s ISOLATION table by design.

## 3. Bring-up order (host)

1. `infra/host/mail/provision-roles.sh --allow-unrestricted` (exit 3 without the
   flag: the pinned build has no per-principal source restriction; the residual
   is inherited by every `kc-*` principal).
2. `gremion-vendor-mail realm-smtp`.
3. `gremion-mail-bringup --assert 1..6b` (asserts 3 and 6b call
   `check-identities` / `realm-smtp`; 6a sends as `system@` from the ACTIVE
   colour's app network; 6a/6b judge the pasted headers with `check-received`).
4. Deliverability record (section 4), then publish DNS edit 4b.

## 4. Deliverability record (TRD-252, PRD-REC-006; Q5, Q6)

Send a test mail (6a) to one large consumer mailbox and to one university
mailbox. For each: confirm inbox (not spam), save the raw headers OFF git, run
`gremion-vendor-mail check-received --file <headers> [--authserv-id <id>]`, and
append one entry to `deliverability/records.json`:

```json
{ "date": "YYYY-MM-DD", "providerClass": "large-consumer", "spf": "pass", "dkim": "pass",
  "dmarc": "pass", "placement": "inbox", "fingerprint": "<check-deliverability-record.mjs --print-fingerprint>" }
```

No address, IP, host or provider name goes into the file (the check refuses
them). Any change to `config.toml.tmpl`, the `STALWART_IMAGE` line or a DKIM
selector line changes the fingerprint and fails `verify` until re-tested.
TASK-038 and gate F2 run `--require`.

## 5. Residuals and hand-offs

- **HIGH (Q13, TASK-042-b):** Stalwart v0.15.5 bans a source after 100 failed
  AUTHs (measured in the scratch run: banned at the 100th, after which the valid
  credential from that source got no answer). `test-smtp` lets every council IT
  admin drive SMTP AUTH from the app tier to `mail.<domain>:587` and probe
  `system@` or another council's `kc-*`, so one admin can get the platform's own
  egress banned. TASK-042-b (or its FU) adds a target deny for `mail.<domain>` /
  `MAIL_BIND_IP(6)`.
- **TASK-043 defect (Q4):** `platformSmtpFromEnv` stamps `platform@` with From
  `no-reply@`; measured on the pinned build that MAIL FROM is refused
  `501 5.5.4`. Customer realms move to `kc-<token>@` with From
  `kc-<token>@<domain>`, display "Gremion". Production `tenant-create` gets the
  platform password only through an operator `-e` today (breaks Q3).
- **Blind spot:** a `docker compose run -e X=...` injection is in no template
  and no render; only `check-secret-separation --host` sees it, while that
  container lives. The running gremion-ui environment is compared by whole
  value (the launcher hands over hashes only), not by substring.
- **kcadm argv:** the Keycloak admin password is on no argv of the docker CLI,
  but `kcadm.sh config credentials --password` still puts it on the java argv
  inside the Keycloak container, visible to host root (realm-smtp, collect,
  gremion-mail-bringup 6b, gremion-neuter). Closing it needs a kcadm
  credential path verified against the pinned Keycloak build.
- **Restored instances (gremion-neuter):** the env keys of every vendor
  credential are blanked (system@, alerts@, roles@, platform@, the Stalwart
  admin password and API key), but the files render-ops.sh derived from them
  (`etc/secrets/ops/smtp-password`, `stalwart-api-key`, the rendered
  Alertmanager config) and the DKIM keys in `etc/secrets/mail` are not
  rewritten by neuter; the restore procedure's owner must re-render or blank
  them before the ops project starts.
- **Assert 6a sends as system@ from the app network** (brief decision): the
  vendor password is in a one-shot probe container's stdin on the active
  colour's app network for the duration of the probe; system@ has no source
  restriction on the pinned build.
- **Receivers:** only `mx.google.com` is committed as a measured authserv-id;
  a receiver whose Authentication-Results carries no authserv-id (reported for
  Microsoft 365) cannot be proven by check-received until its format is
  measured and handled.
- **check-received, remaining trust limits (round-2 review, LOW):** the
  accepting hop is the LOWEST hop from IP-B, so a sender who controls the
  vendor side could pre-write a hop below Stalwart's own; a bare token in a
  from-clause comment is read as an address, and some MTAs write the client's
  HELO there. **from-align.sieve** does not decode comments, quoted group
  names or full-width characters in From, and leaves Sender/Reply-To
  unchecked (display-level only: DMARC alignment still holds).
  **check-secret-separation --host** does not decode percent- or
  JSON-escaped copies of a vendor value, and hashes only the first
  gremion-ui container of each colour.
- **Connection rate limit:** the pinned build limits connections per source IP
  (`[5, 1000ms]`, measured); a burst from one source is delayed, not refused.
- **Host-only (TASK-038 re-runs):** `${STACK}-mail-stalwart` healthy
  (`docker exec`); `--host` separation and principals; bring-up 1..6b green with
  6b's reset mail passing `check-received`; inbox at both provider classes,
  recorded; a customer-realm reset through its own `kc-*` (after TASK-043); one
  alert through `alerts@` (TASK-039); `docs/ops/release-1-waivers.md` gains the
  dated demonstration. Operator items (Q10): IP-B, PTR, port 25.
- **provision-roles.sh owns the whole secret list** of `system@`, `alerts@`,
  `platform@` and `roles@`: each run SETS it to the one generated app
  password (so a rotated-away password stops working), which also removes
  any app password an operator added to one of those principals by hand. Add
  none by hand; a sender that needs its own credential gets its own principal
  (`principals issue`).
- **TASK-015-FU:** `plt.vendor_domain` (DB-MAIL-VENDORDOMAIN) with
  `record-posture.mjs`, and retiring `platform@` (G8) after TASK-043. Decided
  in fix round 2 (2026-09-29) to stay in the FU although TASK-021 is on main
  (the `platform` chain's `0004` is claimable with
  `node scripts/migrations/register.mjs claim --chain platform --name plt_vendor_domain`):
  its TDD item 12 needs a scratch PG18 outside this unit's docker grant, the
  brief's own split rule sends it to the FU, and nothing on the go-live path
  (TASK-039, TASK-043) reads `plt.vendor_domain`.

## 6. Upgrading a host rendered before TASK-015

A host whose env files were rendered from the pre-TASK-015 templates has ONE
`platform_smtp` value in state.env, mail.env, ops.env and the app tier, and
lacks the split. Its signs: `mail.env` has no `VENDOR_SMTP_PASSWORD`,
`ALERT_SMTP_PASSWORD` or `VENDOR_MAIL_NODE_IMAGE`; `ops.env`'s
`ALERT_SMTP_PASSWORD` equals `mail.env`'s `PLATFORM_SMTP_PASSWORD`; `state.env`
still carries `STALWART_ADMIN_PASSWORD`, `STALWART_API_KEY` and
`PLATFORM_SMTP_PASSWORD`. `gremion-init-secrets` will not overwrite existing
files without `--force`, and `--force` regenerates EVERY secret, so it is not
the upgrade path. `gremion-validate-env --env-file etc/env/mail.env --release
current/infra/host/mail` names the missing keys (template key parity), and
`gremion-vendor-mail check-secret-separation --host` fails on the stale
state.env copies.

1. Take a backup (`gremion-backup --label pre-vendor-mail-split`).
2. Generate two new 32-character alphanumeric values, one for `system@` and
   one for `alerts@` -- never reuse the platform value. Add to `mail.env`:
   `VENDOR_SMTP_PASSWORD=<new vendor value>`,
   `ALERT_SMTP_PASSWORD=<new alert value>`, and the
   `VENDOR_MAIL_NODE_IMAGE=` line copied verbatim (digest) from the release's
   `infra/host/templates/env/mail.env.tmpl`.
3. In `ops.env`, set `ALERT_SMTP_PASSWORD` to the SAME new alert value (the
   `alert_smtp` group spans both files), and `ALERT_SMTP_USER` and
   `ALERT_EMAIL_FROM` to `alerts@<PLATFORM_DOMAIN>`.
4. Delete `STALWART_ADMIN_PASSWORD`, `STALWART_API_KEY` and
   `PLATFORM_SMTP_PASSWORD` from `state.env` (nothing reads them there).
5. Re-run `infra/host/mail/provision-roles.sh --allow-unrestricted` (creates
   `system@` and `alerts@`, sets each one's password), `infra/host/ops/render-ops.sh`
   (the Alertmanager SMTP password), restart the ops project, then
   `gremion-vendor-mail realm-smtp`.
6. Prove it: `gremion-validate-env` on each env file, `gremion-vendor-mail
   check-identities`, `check-secret-separation --host`, and
   `gremion-mail-bringup --assert 3`.
